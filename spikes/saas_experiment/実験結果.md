## 3. 本実験

主題は **Turso の Python クライアント3つ**（turso_serverless / pyturso / libSQL）。クラウド DB は同じ東京の `aspara-spike-tyo`。モデルはローカルのまま。バイトを DB に入れない。3つは混ぜて使わない。どれか1つを選ぶための計測。

E1 はリモートのみ、E2 は書レプリカ、E3 は読レプリカ、両方は E2+E3。取れない経路は省略（非対応）。E4 はしない。LTTB / msgpack は E7。Neon は Postgres 対照で、この3つの選択には使わない。

spike の `--backend` は再現用の名前。クライアント名ではない。`turso_sync` は pyturso。`turso_libsql` と `turso_embedded` はどちらも libSQL。

### 3つの違い（先にこれ）

|  | turso_serverless | pyturso | libSQL |
|---|---|---|---|
| PyPI | `turso_serverless` | `pyturso` | `libsql` |
| spike `--backend` | `turso_serverless` | `turso_sync` | `turso_libsql` / `turso_embedded` |
| `log` の書き先 | 雲（HTTP）。100行バッファ | **手元ファイル**。finish で push | 雲（libSQL プロトコル）。100行バッファ |
| `load` の読み先 | 雲 | **手元ファイル**（必要なら pull） | 雲、または埋め込みなら手元（読前 sync） |
| 手元 SQLite ファイル | 無い | 必須 | リモートでは無い。読レプリカでは有る |
| E1 リモート専用 | できる | **できない** | できる |
| E2 書レプリカ | できない | できる | 今回未配線 |
| E3 読レプリカ | できない | できる | できる（埋め込み） |
| E2+E3 両方 | できない | できる | 今回未配線 |
| 他2つとの関係 | リモート専用の公式経路 | レプリカ前提の公式経路。libSQL クライアントは使わない | リモートも埋め込みも同じ `libsql` パッケージ |

同じ「Turso」でも、訓練中にネットへ出るか手元で完結するかが分かれる。turso_serverless と libSQL リモートはどちらもネットへ出す。違うのはドライバと速さ。pyturso だけ訓練ループがローカルになる。

### E4 — しない（モデル → オブジェクトストレージ）

### E5 — finish 直後クラッシュ / resume / 切断 / ジョブ2つ

選んだ経路: pyturso `--mode both`。250 step（正しさ。速さは E2）。空にした `aspara-spike-tyo`（作り直し。後述）。

| 欄 | 記入 |
|---|---|
| 実施 | 実施。`--backend turso_sync` `--mode both`。プロジェクト `saas-e5e7` |
| finish 直後クラッシュ | 手元 250 行・finished。別 data-dir の pull も 250 行・finished。**雲に載る**。3行のまま（スクリプトに sync なし） |
| 学習中の切断 | `os._exit`（finish / close なし）。手元 240 行（flush 100 の分。未 flush の 10 step は消える）。雲は 0 行。**finish の push までリモートに無い** |
| resume | 3行の `init` に resume が無い。同じ名前で再 init すると run_id が変わり、同じ step の flush で UNIQUE。行は消えないが続きも書けない。main は `init(resume=True)` で max(step)+1 |
| ジョブ2つ | 別名なら両方成功、pull で両方見える。同名の二本目は push が UNIQUE で失敗。先に載った 250 行は残る（last-write で消えない） |
| 所感 | 欠けは「未 flush」と「finish 前の雲」。衝突は上書きではなく失敗。resume は main と同じ意味ではない |

特記: bake-off 後の `aspara-spike-tyo` は 145 万行 / レプリカ 209MB。`DROP TABLE` しても同期履歴が残り、空ディレクトリからの connect が遅い・IncompleteRead。Turso は `VACUUM` 不可。**同名 DB を destroy → create** して空にしてから測った。ログインシェルの `TURSO_AUTH_TOKEN` は作り直し後に取り直す。

## 5. 結論（実験後）

**決定（2026-09-25）:** クラウドへ出す経路は **pyturso の書レプリカ** にする。Python クライアントは `pyturso` だけ使う。`libSQL` と `turso_serverless` は製品に入れない。src への移植は main から切った実装ブランチで行う。この実験ブランチの数字が根拠。

選んだ理由: 測ったクラウド経路のうち、訓練ループだけ B0 並み（書レプリカ 0.385–0.476 s）。リモート専用は libSQL でも 66 s。LTTB / msgpack は本線と同じ手続きに載る。読前 pull（both）は閲覧が 20 s 超になるので採用しない。

E5–E7 実施済み。動画なしで取り直しても、訓練ループの大小関係は同じ。

| 見る点 | turso_serverless | pyturso | libSQL |
|---|---|---|---|
| リモート訓練 | 160.0 s。3つの中で最遅 | できない | 66.1 s。3つの中で最速。それでも B0 の 124 倍 |
| 手元に書いて雲へ出す | できない | ループ 0.476 s（B0 並み）。待ちは init の取り込みと finish の push | 今回未測（spike 未配線） |
| 読レプリカ | できない | 初回 21.4 s、そのあと open 0.232 s | 初回 13.1 s、そのあと open 0.225 s |
| 製品に入れるなら | リモート専用のとき | レプリカ前提のとき | リモート専用なら turso_serverless より速い |

モデルのオブジェクトストレージ: 今は見ない。

Polars / LTTB / msgpack: 形とバイトは B0 / B1 と同じ。**書レプリカ**の 3 段は 0.167 s（B0 0.047 s の 3.6 倍、B1 0.033 s の 5.0 倍）。both の読前 pull を足すと 23.6 s。詳細は 4.4。

実装に進むか / やり直す点:

- 3クライアントは排他。pyturso を選ぶなら libSQL パッケージは使わない。turso_serverless を選ぶならレプリカは無い
- src へ移植するなら resume と「同名 run は拒否」を main に合わせる。今の spike は upsert + UNIQUE
- テナント隔離をファイル単位にするなら 1 テナント 1 Turso DB。今は project 列だけ
- 読は pull を毎回やらない（E3 の warm open）。both の load 27.5 s は Dashboard 向きではない
- 実験のあと DB を空にするなら `DROP` では足りない。レプリカが 209MB のまま残る。作り直しが要る
- Neon の訓練を B0 に近づけるなら、flush 間隔や接続の置き方を変えた回を別途（今の E1 数字は flush 100 行）
- Neon 読レプリカを作れば Neon E3 を足せる
- D1 の公式読レプリカは Workers + Sessions API 向け。REST スパイクでは使えず、手元書レプリカも無い。train は速くならない
- libSQL の書レプリカが要るなら spike を足して測る
- 読レプリカの初回秒は、リモート DB に前回実験の行が残っている分だけ長く出る
